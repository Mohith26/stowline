# Stowline

A booking engine for peer-to-peer storage and parking, built around the thing
that makes those listings hard: a listing is a physical rectangle, not a number.

I started this because of a bug class I kept thinking about. If you model a
storage listing as "400 square feet, 200 committed, 200 available," you will
confirm bookings that cannot physically happen. The leftover 200 square feet
might be two disconnected 10 x 10 pockets. Or it might be one clean 10 x 20
strip that happens to sit directly in front of a renter who needs to tow a boat
out in March. Square footage cannot see either problem.

So Stowline answers the booking question geometrically and over time, and then
I measured how much that actually matters.

**It matters a lot. Across 2,400 simulated booking requests, 74.5% of all
rejections were geometric: the square footage was available and there was still
nowhere legal to put the item.**

## The model

The space is a `W x D` rectangle. `y = 0` is the access edge, meaning the garage
door, the mouth of the driveway, the gate of the lot. Each reservation is an
axis aligned rectangle with a half open day interval `[start, end)`.

Three rules:

1. An item is placed once and does not move for the length of its stay.
2. Items whose stays overlap in time may not overlap in space.
3. If item A sits in item B's exit channel, then A's stay must be strictly
   nested inside B's stay.

Rule 3 is the interesting one. An item at depth `y` has to come straight out
toward the door through a channel exactly as wide as it is, so anything sitting
in that channel is in the way. Being in the way is not automatically illegal
though. If you park behind me on Tuesday and leave on Thursday and I am staying
until December, you never actually block me. Formally, A may block B only if
`A.start > B.start` and `A.end < B.end`, so A is gone before either of B's
moving days. That is a strict nesting condition, and it is what turns this from
rectangle packing into something with a time axis that actually bites.

## Layout

```
stowline/geometry.py     rectangles, exit channels, blocking
stowline/timeline.py     interval sweep, peak area, the nesting rule
stowline/placement.py    corner point solver + a complete search used as oracle
stowline/booking.py      the staged booking decision
stowline/search.py       grid spatial index over listings
stowline/pricing.py      locally weighted comp pricing
stowline/generate.py     seeded synthetic market
stowline/experiments.py  every number below
stowline/test_stowline.py
```

No dependencies. `python -m stowline.test_stowline` and
`python -m stowline.experiments <section>`.

## The booking decision is a funnel

Four questions, cheapest first, because the last one is exponential and the
first one is three comparisons.

| stage | question | cost |
| --- | --- | --- |
| dimensions | does it fit the space and clear the opening at all | O(1) |
| area | is there enough square footage at the busiest instant | O(n log n) |
| placement | is there an actual (x, y) that respects everyone | search |
| repack | would it have fit if everyone else could shuffle | search |

The repack stage does not gate anything. I report it because the gap between
"fits" and "would fit if people moved their stuff" is a product decision, not
an engineering one, and it is worth knowing how big it is.

Measured over 60 listings and 2,400 requests (`experiments.py funnel`):

```
accepted                        544  (22.7%)
rejected at dimensions          182
rejected at area                292
rejected at placement         1,382
```

So of 1,856 rejections, **1,382 (74.5%) passed the area check and failed on
geometry**. A capacity counter would have accepted every one of them. Of those
1,382, **243 (17.6%) would have fit if existing renters could be rearranged**,
which is the price of the "we cannot ask people to move their stuff"
constraint, in inventory.

## The solver, and where it is wrong

`solve` is corner point backtracking: place the largest item first, and only
consider x and y coordinates generated by the edges of already placed
neighbours. This is the standard technique for rectangle packing, and for plain
rectangle packing it is complete. Any feasible packing can be slid down and
left until every item touches an edge or a neighbour, and those are exactly the
positions corner point placement tries.

The exit channel constraint breaks that argument, because sliding an item
toward the door is precisely the move that pushes it into somebody else's exit
channel. I did not want to guess whether that costs real solutions, so I wrote
`solve_exhaustive`, the same backtracking search over every integer coordinate
in the space, and ran both on 400 random instances.

```
resolved within budget                384
both agree                            360
fast path missed a real solution       24   (6.25%)
fast path found what oracle could not   0
mean nodes, fast path               11.9
mean nodes, exhaustive          29,943.4   (2,520x)
```

So the fast path is genuinely incomplete here, and I can put a number on it: it
gives up on about one in sixteen solvable instances in exchange for roughly
2,500x fewer nodes. For this problem that is the right trade, since a rejected
booking is recoverable (the renter sees other listings) and a two second search
in the request path is not. But it is a real limitation and I would rather
state it than let the 0 in the "impossible disagreements" row imply the solver
is exact.

That third row is the one I actually watch. `fast_path_found_what_oracle_could
_not` must be zero, because a complete search finding fewer solutions than a
restricted one would mean the two solvers disagree about the rules, not about
the search. It has stayed at zero.

## Verification

`python -m stowline.test_stowline`: **22 cases, 88 assertions, 0 failures, 5.8s.**

The tests that earned their keep are all differential:

- The sweep line `peak_area` is checked against a literal day by day scan on
  3,000 random instances.
- Every arrangement the solver returns is re-validated by `check_placement`, an
  independent O(n^2) recheck that does not share code with the solver, over
  1,500 random instances.
- The grid index is checked against brute force haversine on 400 queries at
  800 listings in the suite, and again on 1,500 queries at 6,000 listings in
  `experiments.py search_exactness`. Zero disagreements in both.
- The fast solver against the complete search, described above.

## Negative controls

Two lines in this codebase are written a particular way for a reason that is
easy to lose in a refactor, and "the tests pass" is not evidence that the
reason was ever real. So rather than assert that the careful version matters,
`stowline/controls.py` reintroduces each mistake deliberately and measures the
damage.

**Converting the search radius to degrees with 69 miles per degree on both
axes.** That figure is right for latitude everywhere and right for longitude
only at the equator. At Lehi's latitude a longitude degree is 52.6 miles, so
the query scans about 76% of the longitude span it needs and silently returns
too few listings. Over 1,200 queries against 8,000 listings, the flat degree
version got **290 queries wrong and dropped 25,456 listings, 3.1% of all true
results**. The correct version got 0 wrong. Nothing throws. A renter just sees
a thinner map than they should.

**Applying arrivals before departures at a shared instant.** With half open
intervals a stay ending on day 40 is already gone when a stay starting on day
40 arrives, and getting the tie order backwards makes two perfectly sequential
renters look simultaneous. On 20,000 instances built to include back to back
stays, the wrong tie order **changes the answer 75.5% of the time, overstating
peak occupancy by 27.5 square feet on average**, which shows up as bookings
rejected at the area gate that were always fine.

Neither of these is exotic. Both are one character of sort order or one
constant, both pass every example based test I would have thought to write, and
both fail quietly in the direction of showing renters less inventory.

## Search

Uniform grid over lat/lon rather than a k-d tree, because listings churn
constantly as hosts add and pause spaces and a grid is O(1) insert and delete
with no rebalancing. The cost is sensitivity to cell size, so I swept it at
20,000 listings:

| cell (deg) | queries/sec | mean candidates examined |
| --- | --- | --- |
| 0.01 | 1,656 | 883 |
| 0.02 | 1,566 | 1,069 |
| 0.05 | 1,282 | 1,354 |
| 0.10 | 649 | 2,751 |
| 0.25 | 210 | 8,601 |

Brute force over the same 20,000 listings runs 97.9 queries/sec, so the best
cell size is **16.9x faster** while returning an identical result set.

## Pricing

Locally weighted median of comparable listings' price per square foot, with a
Gaussian kernel on distance and a log-ratio kernel on size, then a size
adjustment and a gentle clipped utilization multiplier. Weighted median rather
than mean because storage comps have a long right tail and one climate
controlled indoor unit should not drag the recommendation for a dirt lot.

Against a held out truth over 1,200 listings, scoring 347 targets:

```
model MAPE                    0.1285
global median baseline MAPE   0.2468   (47.9% worse)
53 targets got no recommendation at all (too few effective comps nearby)
```

Refusing to answer is a feature. A pricing recommendation built from 1.4
effective comps is worse than no recommendation, because the host will believe
it.

The size exponent sweep produced the one result here I did not expect:

| exponent | MAPE |
| --- | --- |
| 0.00 | 0.1378 |
| -0.05 | **0.1285** |
| -0.10 | 0.1287 |
| -0.15 | 0.1422 |
| -0.20 | 0.1616 |
| -0.30 | 0.2103 |

The synthetic market is generated with a -0.15 size exponent. Using -0.15 in
the estimator is measurably worse than -0.05. The reason is that the comp
kernel already weights on log size similarity, so the comps that survive it are
mostly the same size as the target and their prices already carry the discount.
Applying the full curve on top double counts it. Matching the data generating
process is not the same thing as minimising error through a pipeline that has
already conditioned on the same variable. I moved the default to -0.05 and left
the sweep in `experiments.py` so the choice is auditable.

## Throughput

On a listing that already holds 6 reservations, 4,000 booking decisions
(dimensions, area, and the full placement search) run at **37,383 decisions per
second, 26.7 microseconds each**, single threaded. That is comfortably inside a
request path. The funnel experiment runs slower at 647 decisions/sec because it
also runs the counterfactual repack search on every geometric rejection, which
is offline work.

## What I left out

- Items do not move mid stay. Real hosts do consolidate between renters, and
  modelling that turns each booking into a rescheduling problem rather than a
  placement problem.
- The exit channel is a straight vertical strip. A real garage with a corner to
  turn needs a swept path, which is a different geometry problem.
- One access edge per listing. A corner lot has two.
- Prices are static per listing rather than seasonal, and storage demand is
  visibly seasonal (boats and RVs go away in October).
